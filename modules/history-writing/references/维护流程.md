# 维护流程

新增内容由用户提供的目录或文件进入，原文件保持不变。正常选题与写稿不修改技能库。发布副本仅保存库内快照路径和内容哈希，不保留原电脑目录、原文件名或个人采集时间；私有来源映射放在技能目录之外。

1. 用 `scan` 只读对比新增、内容变化和当前目录未发现的原件。对比依据 SHA256；缺失仅是检查结果，不触发删除。改过的旧稿保存新版本，不覆盖旧快照。
2. 读取新增全文，确认正文完整、账号、平台、视频 ID、指标与采集日期。没有发布日期就保留空值。相同视频 ID、相同正文、改名重复、同故事不同讲法分别处理；只把达到用户筛选条件的稿件纳入正式高赞库。
3. 为每篇分配下一个未用 H 编号，保存字节不变的 `corpus/raw/Hxxx.md` 和原始 SHA256。清洗结果另存 `clean/`，逐项记录改动；不自动改正不确定人名。沿用现有 `meta/Hxxx.json` 的完整字段，人工补时代、人物、冲突、模板、结构、故事簇、来源性质、风险与新角度。`fact_status` 默认未整体核实。
4. 用结构化 JSON API 合并 `catalog.json`，确保其每项与对应 meta 一致。更新可读选题库。新主题如果仅一两篇，先标尝试，不贸然成为全局规则。
5. 重新统计受影响的分布；`statistics.json` 是首批 57 篇的快照，未重算时必须在新版本说明保留为旧快照，不让它冒充更新后的统计。统计方法见语言文档；新增风格规则需有跨篇证据，并选此前未参与归纳的材料回查。
6. 开头专项也随语料更新：逐篇补 `corpus/hook_annotations.tsv` 的主辅类型、原文张力线索与单元末尾、首句任务、推进、承诺和风险，不能按关键词自动替代语义判读。在私有仓库运行 `python -X utf8 tools/build_hooks.py` 重建 JSON 和逐篇分析；该仓库维护工具不随使用副本安装。同步修订开头指南里的统计、边界与证据，不把新增样本冒充既有验证。
7. 运行 `validate`；检查原始哈希和路径，再做一次新题试写及字数校验。开头更新需试验同题多版的区别、事实一致性、只要钩子时的停止位置及短时长计数。先在副本完成和验证，再更新已安装版本；不在写稿过程中后台修改规则。

8. 本目录是 story-studio 的内置使用副本；这里只更新用户明确要求维护的内置资源并校验，不自动发布或修改其他安装目录。

完整语义蒸馏由读取本技能的助手完成，`scan` 只负责可靠识别文件变化，不声称自动完成新稿理解。用户项目的已用题记录单独维护，不能把“生成”当作“发布”。
